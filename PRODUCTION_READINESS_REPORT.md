## 3. PostgreSQL RLS & Supabase Connection Audit

### Audit Checks:
- Inspected environment variables for Supabase configuration:
  - `DATABASE_URL`: `None`
  - `SUPABASE_URL`: `None`
  - `SUPABASE_SERVICE_KEY`: `NOT SET`
- Checked local PostgreSQL services:
  - `Get-Service *postgres*`: No service installed.

### Architecture Analysis of RLS in the Backend:
In `backend/app/database.py`, the backend connects via SQLAlchemy asyncpg pooler. 
- The policies in `backend/sql/rls_policies.sql` use `auth.uid() = user_id`.
- Script updated to cover all new private tables (`user_upload_permissions`, `user_processing_history`, `review_queue`, `question_similarity_reviews`) while granting `SELECT` on shared tables (`shared_historical_papers`, `shared_verified_questions`, etc.) to authenticated users.
- When FastAPI connects directly via pooler as the database owner/superuser, PostgreSQL bypasses RLS by default.
- **Defense-in-Depth Implementation:** All queries in `papers.py`, `questions.py`, `analysis.py`, etc., strictly enforce `WHERE user_id == current_user.id` at the SQLAlchemy application layer.
- Cross-user isolation was verified via automated integration tests (`test_cross_user_isolation.py`, `test_cross_user_shared_growth.py`, and `test_4_cross_user_isolation` in `test_security_acceptance.py`).

**Status:** **APPLICATION-LAYER ISOLATION VERIFIED; LIVE SUPABASE RLS UNTESTED DUE TO ABSENCE OF SUPABASE CREDENTIALS.**

## 7. Render Restart Recovery & Session Expiration

### 1. Interrupted Extraction Recovery
- **Scenario:** Render spins down or restarts while a PDF extraction is in `EXTRACTING` state.
- **Code:** `recover_stalled_paper_extractions()` in `backend/app/services/ingestion_service.py` is invoked during FastAPI `lifespan` startup.
- **Verification:** Automatically queries `papers.status == 'EXTRACTING'` and resets them to `FAILED` with retry notes. Tested and verified in `test_restart_recovery_for_stalled_extractions`.

### 2. Session Invalidation & Expiration
- **Scenario:** Ephemeral RAM session keys expire after 120 minutes of inactivity or upon explicit logout.
- **Verification:** Tested in `test_session_expiration` and `test_logout_credential_invalidation`. Keys are wiped from server memory.
